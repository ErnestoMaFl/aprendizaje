Lección 03 · JavaScript del 80%

Cuando JavaScript convierte por su cuenta

Al corregir el Reto 01 hiciste la pregunta que abre esta lección: sabías que "Ana" caía en el primer parámetro, pero no entendías por qué el resultado era el texto "Ana, undefined" y no un undefined a secas. La respuesta es que JavaScript convierte valores de un tipo a otro sin avisar, y hay que saber exactamente cuándo. Al terminar podrás predecir el resultado de cualquier operación entre tipos distintos — que es de dónde sale la mitad de los bugs raros que verás en código ajeno.

Antes de empezar: tres de memoria

De sesiones anteriores, y sin volver atrás a mirarlo. Recordar cuesta más que releer, y ese esfuerzo es justo lo que hace que se te quede. Si alguna no sale, no pasa nada: sirve igual.

Calentamiento 1
Con base valiendo 1000, ¿cuánto vale esta expresión? 

base + base * 0.21

Correcto: 1210. La multiplicación va primero (1000 × 0.21 = 210) y luego la suma. Cerrado el tema.
Es 1210. * se resuelve antes que +: primero 1000 * 0.21 = 210, después 1000 + 210. Si hubiera paréntesis —(base + base) * 0.21— sería 420.

Calentamiento 2
Una de estas líneas revienta. ¿Cuál? Responde con su número. 

1  const tarifa = { hora: 40 };
2  let horas = 10;
3  tarifa.hora = 50;
4  tarifa = { hora: 60 };
5  horas = 12;

Correcto: la 4. La 3 abre la caja y cambia algo de dentro — permitido. La 4 despega la etiqueta tarifa para pegarla a otra caja — eso es reasignar, y const lo prohíbe: TypeError. La 5 va bien porque horas es let.
Es la 4. Distingue los dos gestos: la línea 3 abre la caja y cambia una propiedad de dentro (const lo permite), mientras que la 4 despega la etiqueta para pegarla a un objeto nuevo (const lo prohíbe → TypeError). La 5 no falla: horas se declaró con let.

Calentamiento 3
¿Qué devuelve tercio(9)? 

const tercio = (x) => { x / 3; };

Correcto: undefined. Hay llaves ⇒ es un bloque ⇒ hace falta return, y no está. Calcula el 3 y lo tira. Este es el que fallaste en el Reto 01: ahora sale solo.
Es undefined, y es el tercer encuentro con este mismo fragmento (Lección 02 y Reto 01). La regla completa: llaves después de la flecha ⇒ bloque ⇒ hace falta return. Sin return, la función termina y devuelve undefined en silencio. Para que devolviera 3: (x) => x / 3.

La apuesta: predice antes de leer nada

Cinco expresiones. Todas son legales, ninguna da error, y ninguna hace lo que parece. Escribe lo que crees que sale. Fallar aquí es parte del método: la apuesta abre el hueco que luego rellena la explicación. 

"Ana, " + undefined
"5" + 3
"5" - 3
1 + 2 + "3"
"5" == 5

Todo valor en JavaScript tiene un tipo. Son pocos, y con seis ya lees el 99% del código. typeof te dice el de cualquier valor:

Los dos vacíos: undefined y null

Ya conoces undefined: es el vacío que pone JavaScript —una función sin return, un argumento que no pasaste—. null es el vacío que escribe una persona a propósito, para decir «aquí no hay nada, y lo sé». Mismo significado práctico, distinto origen.

Y ese typeof null === "object" de la tabla es un bug de 1995 que nunca se arregló porque rompería media web. No lo entiendas: reconócelo. Es la primera pieza de periferia que te encuentras. reconocer

2. El + son dos operadores disfrazados de uno

Aquí está la respuesta a tu pregunta. El + mira sus dos lados y decide:

La regla del +

Si alguno de los dos lados es texto, el + pega (y convierte el otro lado a texto para poder pegarlo). Si ninguno lo es, suma. 

"Ana, " + undefined   // "Ana, undefined"  ← hay texto: pega
"5" + 3              // "53"             ← hay texto: pega
5 + 3                // 8                ← no hay texto: suma

Por eso saludar("Ana") devolvía "Ana, undefined": el undefined no «contamina» la expresión entera, sino que se convierte al texto "undefined" —cinco letras y ya— y se pega como cualquier otra palabra. JavaScript no distingue entre «un texto que quiero mostrar» y «un agujero»: para él ambos son cosas que se pegan.

Y ese es exactamente el motivo de que sea peligroso, que era tu propia conclusión en el reto: si undefined reventara, lo verías en el momento. Como se convierte en texto, llega hasta la pantalla del cliente convertido en "Total: undefined €".

El orden importa: se resuelve de izquierda a derecha

Cuando hay varios + seguidos, se aplican por parejas, empezando por la izquierda. Cambia el orden y cambia el resultado: 

1 + 2 + "3"     // (1 + 2) = 3, luego 3 + "3" → "33"
"3" + 1 + 2     // ("3" + 1) = "31", luego "31" + 2 → "312"

3. Los demás operadores solo saben de números

-, *, / y % no tienen doble personalidad: convierten los dos lados a número y operan, pase lo que pase. Por eso "5" - 3 da 2 mientras que "5" + 3 daba "53". Es la asimetría que más desconcierta al principio.

Dos caracteres invisibles que verás escritos

Dentro de un texto, \n significa salto de línea y \t un tabulador. Se escriben con dos caracteres pero valen uno solo. Cuentan como espacio en blanco, así que " \t \n" convertido a número da 0, igual que " ".

Fíjate en las dos filas rojas: son las dos únicas que producen NaN, y entre ellas está la que ya te mordió en el Reto 01. suma(7) dejaba b valiendo undefined, y 7 + undefined no tiene ningún texto por medio ⇒ el + suma ⇒ convierte undefined a número ⇒ NaN. Las dos reglas encajan.

NaN: el número que no es un número

NaN («Not a Number») es de tipo "number" —sí, en serio— y es contagioso: cualquier cuenta que lo toque devuelve NaN. Un solo dato mal convertido al principio de un cálculo lo envenena entero. 

"4px" - 2          // NaN
("4px" - 2) * 100  // NaN — el veneno se propaga

Rareza que conviene conocer: NaN no es igual ni a sí mismo. NaN === NaN es false. Para detectarlo existe Number.isNaN(valor), que devuelve true o false. núcleo

4. Convertir a propósito

Todo lo anterior es JavaScript convirtiendo solo. Lo que se escribe en código real es la conversión explícita, porque se ve y no sorprende a nadie: 

Number("42")    // 42     — texto a número
String(42)      // "42"   — número a texto
+"42"            // 42     — atajo: un + delante convierte a número

Ese + solitario delante de un valor se llama + unario y es el mismo Number() escrito corto. Lo verás mucho. Ojo con no confundirlo: +"42" (un solo operando) convierte; "4" + "2" (dos operandos) pega.

Por qué esto te importa en las webs que entregas

Todo lo que escribe un usuario en un formulario llega a tu JavaScript como texto, siempre — aunque el campo sea de tipo número. Si un cliente teclea 1200 y tú haces precio + 100, obtienes "1200100" y no 1300. Este es literalmente el bug número uno de quien empieza con formularios, y se arregla con un Number(...) en el sitio correcto.

5. Comparar: === siempre

JavaScript tiene dos operadores de igualdad, y la diferencia es exactamente la conversión automática:

OperadorQué haceEjemplo
=== núcleoCompara valor y tipo. No convierte nada."5" === 5 → false
== solo leerConvierte primero, compara después."5" == 5 → true
!== núcleoEl contrario de ===."5" !== 5 → true

La regla práctica cabe en una línea: usa === siempre. No es una preferencia de estilo — las reglas de conversión de == son tantas y tan arbitrarias que ni la gente que lleva años escribiendo JavaScript se las sabe de memoria. Escribiendo === no tienes que saberlas.

La única excepción que se usa de verdad

null == undefined es true: es una regla especial, y son los únicos dos valores que == considera iguales entre sí. Ningún otro valor es == a null — ni el 0, ni el texto vacío.

Por eso x == null se escribe a propósito: pregunta «¿está vacío, de cualquiera de las dos formas?» en un solo gesto. Con === harían falta dos comparaciones. Es la excepción, no la norma.

Comparar textos con < y >

Dos textos no se comparan por longitud, ni por lo que valdrían como número. Se comparan como en un diccionario: carácter a carácter, de izquierda a derecha, y el primero que difiere lo decide todo. A partir de ahí ya no se mira nada más. 

"2" > "12"

  posición 1:  "2"  contra  "1"
               ¿cuál va después en el orden? El "2".
               Decidido: "2" es mayor.  →  true

               El "2" que queda en "12" ni se llega a mirar.

Es la lógica del diccionario de toda la vida: «zapato» va después de «abecedario» aunque «abecedario» tenga el triple de letras. Nadie cuenta letras; se mira la primera que difiere —z contra a— y se acabó.

Con textos que parecen números, eso da resultados que parecen absurdos y son consistentes:

"9" > "100"   // true  — mira "9" contra "1"
"10" < "9"    // true  — mira "1" contra "9"

"2" > 12       // false — aquí NO son dos textos: hay un número,
                //         así que convierte y compara 2 > 12

Por eso una lista de precios o de fechas guardados como texto sale desordenada, y por eso se convierte a número antes de comparar. Misma moraleja que el resto de la lección.

Pregunta 1 · escribe la respuesta
¿Qué imprime? (el valor exacto) 

console.log("1" + 1 + 0);

Correcto: el texto "110". De izquierda a derecha: "1" + 1 encuentra un texto ⇒ pega ⇒ "11"; luego "11" + 0 ⇒ "110". Una vez que la cadena se vuelve texto, ya no vuelve a ser número.
Es "110", un texto. Resuélvelo por parejas desde la izquierda: "1" + 1 → hay texto, así que pega → "11". Después "11" + 0 → "110". El error típico es sumar primero 1 + 0: los + no se saltan el orden.

Pregunta 2 · escribe la respuesta
¿Y este? (el valor exacto) 

console.log("  6  " / "3");

Correcto: el número 2. La división no tiene doble personalidad: convierte los dos lados a número. Los espacios de los bordes se ignoran, así que " 6 " → 6 y "3" → 3.
Es 2, y además un número de verdad, no un texto. Solo el + tiene doble comportamiento; -, *, / y % convierten siempre a número. Los espacios de los extremos no estorban: " 6 " vale 6.

Pregunta 3
Un campo de formulario vacío llega a tu código como texto vacío "". ¿Qué imprime esto? 

const horas = "";
console.log(horas * 40);

Correcto: 0. El texto vacío convertido a número es 0, y 0 * 40 = 0. Y ahí está el peligro real: un campo sin rellenar no te avisa con un error, te factura 0 € con total naturalidad.
Da 0. Repasa la tabla: el texto vacío "" convertido a número es 0 (no NaN — para eso haría falta un carácter que no encaje, como en "4px"). Así que 0 * 40 = 0. Un formulario a medio rellenar produce un presupuesto de cero euros sin quejarse.

Pregunta 4
¿Cuál de estas tres comparaciones es true?

Correcto. null == undefined es la regla especial: con ==, los dos vacíos se consideran iguales. Con === no, porque son de tipos distintos. Y NaN no es igual ni a sí mismo, con ningún operador.
La verdadera es null == undefined. Con === son distintos (tipos distintos), y NaN === NaN es false siempre — NaN es el único valor de JavaScript que no es igual a sí mismo; por eso existe Number.isNaN().

Pregunta 5 · escribe la respuesta
Una función devuelve undefined por olvidar el return, y su resultado se usa en una cuenta. ¿Qué imprime? 

const base = (n) => { n * 2; };
console.log(base(10) - 5);

Correcto: NaN. Dos lecciones encadenadas: el bloque sin return devuelve undefined, y undefined convertido a número es NaN. Así es como un return olvidado aparece disfrazado de NaN tres funciones más allá.
Es NaN. Encadena las dos reglas: base(10) tiene llaves sin return ⇒ devuelve undefined. Luego undefined - 5 usa el guion, que convierte a número ⇒ undefined es NaN ⇒ el resultado es NaN. Este encadenado es exactamente cómo se ven estos bugs en la vida real.

Pregunta 6 · escribe la respuesta
¿Qué operador de igualdad debes escribir tú, por defecto, en todo tu código?

Correcto: ===. Compara valor y tipo sin convertir nada, así que no tienes que memorizar ninguna tabla de conversiones. == se aprende solo para leer código ajeno.
La respuesta es === (y su contrario !==). No convierte nada, así que es predecible sin memorizar reglas. == queda para leer código de otros — y para el caso especial x == null.

Tu misión de lectura

Calculadora de presupuesto de una web de cliente. Los tres primeros valores son lo que llega de un formulario — y de un formulario siempre llega texto, aunque el campo sea numérico. Léelo sin ejecutarlo. 

// Lo que el cliente escribió en el formulario (siempre texto):
const horas = "20";
const tarifa = "45";
const extra = "";          // campo que dejó vacío

const subtotal = (h, t) => h * t;
const conExtra = (s, e) => s + e;

console.log(subtotal(horas, tarifa));            // a)
console.log(conExtra(900, extra));              // b)
console.log(conExtra(900, "150"));             // c)
console.log(subtotal(horas, tarifa) === 900);  // d)

a) ¿Qué imprime, y de qué tipo es?   b) ¿Y esta?   c) Esta es la que factura mal de verdad. ¿Qué sale y por qué es grave?   d) ¿true o false?   e) Arregla conExtra para que sume siempre, escriba lo que escriba el cliente.

Pista (si la necesitas)
Ve valor por valor preguntándote solo dos cosas: ¿alguno de los dos lados es texto? y ¿qué operador es? Recuerda que * siempre convierte a número, y que + solo suma si ninguno de los dos lados es texto. Para e), mira la sección «Convertir a propósito».
Ver la solución (solo después de escribir la tuya)

a) 900, y es un número. * convierte los dos textos a número: 20 * 45. La multiplicación se salva sola.
b) "900", un texto. extra es "", que es texto ⇒ el + pega en vez de sumar. Parece correcto en pantalla y ya no es un número.
c) "900150". Un extra de 150 € convierte un presupuesto de 900 en uno de novecientos mil ciento cincuenta. Es grave porque no da ningún error: sale a pantalla, o al PDF, o al correo del cliente.
d) true. subtotal devuelve el número 900, mismo valor y mismo tipo que 900. (Si hubiera devuelto "900", sería false.)
e) const conExtra = (s, e) => Number(s) + Number(e); — o con el atajo: (s, e) => +s + +e;. Convertir antes de operar es la solución a toda esta lección.

Lo importante de a) frente a b): el mismo par de textos da un número o un texto según el operador. Por eso el error se cuela — la mitad del código funciona.
